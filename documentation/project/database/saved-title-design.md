# Saved titles: first data model and API contract

Status: initial implementation in progress. Supabase Auth, TMDB verification before saving, immediate deletion of account records upon account deletion, and the initial statuses and one-status-per-title model were selected. The saved-title table, owner-scoped API role, and initial FastAPI endpoints are implemented; runtime configuration and full end-to-end verification remain necessary. Open model and API decisions remain for team review.

## Goal and boundaries

A signed-in user can save a movie or TV show from TMDB, see and change its status, and remove it. Records belong to the signed-in user and persist in Supabase PostgreSQL. Visitors can search and browse the catalog without signing in. TV entries also support episode progress as described below. Ratings, recommendations, and full title metadata are separate work.

React uses Supabase Auth for account and session flows. It sends a Supabase access token to FastAPI over HTTPS as `Authorization: Bearer <access_token>`. FastAPI validates the token using Supabase's supported verification method, including signature, issuer, audience, and expiry, and derives the user ID from the verified token. Never accept an owner ID from the request body as proof of identity. Use only a publishable key in browser code; never expose service-role credentials. Registration, verification, reset, and session handling still need implementation and testing.

## Proposed table: `saved_titles`

| Field | Type | Purpose |
| --- | --- | --- |
| `id` | UUID, primary key | Stable identifier for the saved record, generated by the database. |
| `user_id` | UUID, required | References the Supabase Auth user; derived from verified identity. |
| `media_type` | text, required | `movie` or `tv`; TMDB IDs can overlap between types. |
| `tmdb_id` | positive integer, required | Identifies the title within its media type. |
| `status` | text, required | One of the allowed statuses for the media type below. |
| `created_at` | timestamp with time zone | When the record was created. |
| `updated_at` | timestamp with time zone | When the record was last changed. |

Enforce uniqueness on `(user_id, media_type, tmdb_id)` and validate allowed types, positive IDs, and type/status combinations in the database as well as the API. When an account is deleted, all of its account records must be deleted immediately. For `saved_titles`, use a foreign key with cascade on deletion of the Auth user; future account-owned tables and any external copies also need a deletion design and verification. FastAPI scopes every query and mutation to the verified user. If a role subject to row-level security accesses this table, enable RLS and create and test explicit owner policies for select, insert, update, and delete. Privileged roles can bypass RLS, so server-side authorization remains mandatory.

Agreed initial statuses:

| Type | Statuses |
| --- | --- |
| Movie | `watchlist`, `watched` |
| TV show | `watchlist`, `watching`, `completed`, `paused`, `dropped` |

These follow the current user stories. A record can represent only one status at a time. Whether users can move between all statuses remains open; the initial proposal allows any valid status transition. The UI can obtain title names and posters from TMDB; this table does not require storing copies of the catalog. Missing or unavailable TMDB metadata must not remove a saved record.

## Proposed API

All paths below require a verified bearer token. JSON uses snake_case. Examples omit the base URL.

| Method and path | Purpose | Successful result |
| --- | --- | --- |
| `GET /api/me/saved-titles` | List only the caller's entries. Optional `status` and `media_type` filters. | `200` and `{ "items": [...] }`; an empty list is valid. |
| `POST /api/me/saved-titles` | Create an entry from `media_type`, `tmdb_id`, and `status`. | `201` and the created entry; duplicate is `409`. |
| `PATCH /api/me/saved-titles/{id}` | Change the status of the caller's entry. | `200` and the updated entry. |
| `DELETE /api/me/saved-titles/{id}` | Remove the caller's entry. | `204`, empty body. |

Example create request:

```json
{ "media_type": "tv", "tmdb_id": 1396, "status": "watchlist" }
```

Example response, with illustrative values:

```json
{
  "id": "a5a4d9ea-c10f-458b-a89e-4ed85d78c8fa",
  "media_type": "tv",
  "tmdb_id": 1396,
  "status": "watchlist",
  "created_at": "2026-11-16T12:00:00Z",
  "updated_at": "2026-11-16T12:00:00Z"
}
```

Before creating a saved record, FastAPI must verify with TMDB that the ID exists for the requested media type. If TMDB confirms it does not exist, reject the request without creating a record. If TMDB cannot be reached or returns a transient error, report a retryable upstream failure and do not save an unverified title; do not misrepresent an outage as a nonexistent title. Existing saved records remain intact during an outage. Exact error response codes and format for these cases remain to be agreed.

Use `401` for missing, expired, or invalid tokens; `404` for an entry absent from the caller's library, including another user's ID; `409` for a duplicate; and `422` for invalid input. Return a consistent error shape to be agreed across the API; do not leak secrets or private records. The unique database constraint handles concurrent duplicate requests.

## First verification cases

- Two accounts can save the same title independently; the same account cannot create a duplicate for one media type and ID.
- Movie and TV IDs are distinct, invalid statuses are rejected, and valid status changes persist.
- An unauthenticated request is rejected; one account cannot list, change, or delete another account's record, even when it knows the ID.
- Removing an entry persists; an empty library returns an empty list. Test behavior when TMDB is unavailable.
- Verify token validation and, if used, RLS with real non-privileged test accounts; never use service-role credentials in the frontend.
- Confirm TMDB rejects nonexistent IDs and mismatched media types, and that a TMDB outage does not create an unverified record or erase existing entries.
- Verify account deletion removes its saved records and all other account-owned records, without affecting other users.

## TV episode progress

`watched_episodes` stores unique season/episode selections against the owner and TMDB TV title. Progress survives removal of the saved title and is restored when it is re-added; deleting the account removes the history. The backend verifies TMDB episode numbers before marking them watched; unmarking does not require TMDB so existing selections can be removed during an outage. Browser database roles have no direct access.

Authenticated routes under `/api/me/saved-titles/{id}` provide `GET /episodes`, `PUT` and `DELETE /seasons/{season}/episodes/{episode}`, and `PUT` and `DELETE /seasons/{season}/episodes`. Season marking adds the episodes currently returned by TMDB; season unmarking removes all recorded selections for that season. The library reports the episode following the most recently marked watched episode, including season zero where applicable. Unmarking it selects the remaining most recently marked episode; marking a whole season makes its final episode most recent. If metadata needed to determine it is missing, it reports the next episode as unavailable instead of guessing. These choices remain provisional pending the team decisions on out-of-order selections and changed metadata.

## Team decisions before implementing

1. Confirm allowed status transitions.
2. Agree API-wide error format and upstream-error codes, pagination as the library grows, and whether saved libraries will ever be visible to others. This first contract is owner-only.
3. Select and test the exact Supabase token verification and database role/connection approach before enabling account-owned writes.
4. Design and test account deletion across every account-owned table and any external copies as those resources are introduced.
